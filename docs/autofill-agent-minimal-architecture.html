Minimal Autofill Agent Architecture

Smallest useful service architecture for applying to events with reusable form automation, immutable automation bundles, scoped user-data packages, and fill-and-submit Playwright execution.

Goal

Define the smallest useful architecture for applying to events using reusable form automation.

Events-service

Event collection, identification, application URL metadata, and event type ownership.

User-data-service

User data storage, processing, contract fulfillment, preview, and scoped execution access.

Application-process-service

Application job management, orchestration, policy evaluation, tracking, and notifications.

Autofill-service

Automation bundle generation and Playwright execution.

V1 supports only regular events. Events that require CAPTCHA or authentication are classified and stopped until separate pipelines are designed.

Core Principles

  • Application-process-service orchestrates the workflow.
  • Autofill-service owns automation bundles and execution queues.
  • Events-service owns event type classification.
  • User-data-service owns user data and returns data package references, not reusable raw profile access.
  • Application-process-service stores references and decisions, not long-lived copies of resolved user data.
  • Automation bundle versions are immutable.
  • Production autofill execution is always fill-and-submit; user review happens before execution is queued.

    else no ready bundle
      APS->>AFS: CreateBundleRequest(application_url,event_type,metadata)
      loop poll bundle status
        APS->>AFS: Get bundle status
        AFS-->>APS: generating | ready | unsupported | failed
      end
    end
    alt bundle unsupported
      APS->>ES: Forward discovered event type
      APS-->>User: Notify unsupported
    else bundle ready
      APS->>UDS: Create data request(contract + job context)
      loop poll data request
        APS->>UDS: Get data request status
        UDS-->>APS: pending | incomplete | ready | failed
      end
      alt incomplete
        APS-->>User: Notify missing data
      else ready
        UDS-->>APS: data_package_id + package metadata
        APS->>APS: Evaluate review_all/review_risky/auto policy
        opt review required
          APS->>UDS: GET package preview
          UDS-->>APS: display-safe preview
          APS-->>User: Request approval
          User-->>APS: Approve
        end
        APS->>UDS: Create scoped read-only data_access_grant
        APS->>AFS: Create execution(bundle + package + grant)
        AFS->>UDS: Fetch execution data using grant
        AFS->>AFS: Fill and submit with Playwright
        AFS-->>APS: Execution result/evidence summary
        APS-->>User: Notify succeeded or failed
      end
    end
  end

Event Types

Events-service owns event type:

regularwith_captchawith_authunknown

V1 proceeds only for regular and unknown. If Autofill-service discovers CAPTCHA or auth during bundle generation, it reports the discovered type to Application-process-service. Application-process-service forwards the update to Events-service, marks the application job as unsupported, and notifies the user.

Application identity and active-job dedupe key:

user_id + event_id + application_type

Automation Bundle

An automation bundle automates one application form for one event and application type.

Bundle identity = event_id + application_type + version

Each bundle version is immutable. Its user_data_contract is also immutable. If the form changes, Autofill-service creates a new bundle version with a new contract.

Status and blockers

Status: created, preparing, waiting, executing, succeeded, failed, unsupported, cancelled, expired.

Blocking reason: bundle_generation, user_data_resolution, user_data, approval, autofill_execution, unsupported_event_type, operator, none.

User Application Policy

review_all

Always requires user approval after user data is ready and before autofill execution is queued.

review_risky

Requires approval only if the data package contains risky fields such as low confidence, sensitive data, required consent, or confirmation flags.

auto

Queues autofill execution automatically if all required data is available, valid, and allowed to use. System safety rules may still override.

User Data Request

User-data-service owns data resolution and package creation. Application-process-service creates an async data request using user_id, application_job_id, event_id, application_type, bundle_id, bundle_version, and user_data_contract.

StatusMeaningApplication-process behavior
readydata_package_id is available and contract is fulfilled.Evaluate application policy.
pendingUser-data-service is still resolving/extracting data automatically.status=preparing, blocking_reason=user_data_resolution.
incompleteUser action is needed to update/provide data.status=waiting, blocking_reason=user_data, notify user.
failedSystem error or contract cannot be processed.status=failed.

User-data-service does not notify the user directly; it returns structured missing-data/action information to Application-process-service, which owns user notifications.

Data Package References and Review Preview

  1. User-data-service creates a data package.
  2. User-data-service returns data_package_id and metadata to Application-process-service.
  3. Application-process-service evaluates policy using package metadata and preview APIs.
  4. Application-process-service sends only a package reference and scoped access grant to Autofill-service.
  5. Autofill-service fetches execution data directly from User-data-service.

Review preview API

GET /user-data/packages/{data_package_id}/preview

Preview contains display-safe fields: contract field id, label, display value, source, confidence, risk flags, sensitive category, and confirmation requirements. Application-process-service stores only approval decision/reference fields.

Autofill Execution

Autofill-service owns execution queue and execution state. Production execution is always fill-and-submit. If user review is required, it happens before execution is queued.

CreateExecutionRequest

  • application_job_id
  • bundle_id
  • bundle_version
  • data_package_id
  • data_access_grant

The grant must be job-scoped, bundle/version-scoped, contract-scoped, read-only, and short-lived.

Execution statuses

queuedrunningsucceededfailed

Failure reasons: site_unreachable, form_changed, validation_error, submission_rejected, timeout, unknown.

Execution evidence

Autofill-service owns detailed browser evidence and artifacts. Application-process-service stores only summary references such as autofill_execution_id, terminal status/reason, submitted_at, and evidence_ref or screenshot_ref.

Minimal Workflow

  1. Create application job. Create or return an active deduplicated job by user_id + event_id + application_type.
  2. Load event metadata. Stop as unsupported for with_captcha or with_auth; continue for regular or unknown.
  3. Get or create automation bundle. Request async bundle generation if no ready bundle exists; handle ready, generating, unsupported, and failed.
  4. Request user data. Create an async data request using the bundle's immutable contract; handle ready, pending, incomplete, and failed.
  5. Evaluate application policy. Fetch preview and wait for approval when required; otherwise continue automatically.
  6. Queue autofill execution. Send application_job_id, bundle id/version, data_package_id, and a scoped data access grant.
  7. Poll execution and notify. Store evidence summary and notify on success/failure.

V1 Non-Goals

  • CAPTCHA application pipeline.
  • Authenticated application pipeline.
  • Browser-session resume after interruption.
  • Post-fill browser preview before submit.
  • Application-process-service storing long-lived resolved user data.
  • Cross-job learning from executions.
  • Multiple application forms without explicit application_type.
