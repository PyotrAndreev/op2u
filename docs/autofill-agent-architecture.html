1. Service Boundary

Autofill owns
  • form automation
  • bundle lifecycle
  • sandbox execution
  • final execution/submission policy
  • submission evidence and automation audit
User-data service owns
  • user data access
  • LLM extraction from user data
  • missing-data collection
  • asset library access
  • provenance, confidence, and data-level permission flags

Data boundary: autofill never receives raw unstructured user data. It requests contract-scoped resolved data only after a bundle is active.

3. Component Architecture

4. Required Data Contract

Autofill sends a rich machine-readable contract to user-data service. It must be complete; user-data should not need to request more form context.

Field identity

  • contract field id
  • semantic type
  • original label/help text
  • branch condition

Constraints

  • required/optional
  • format/type/length
  • enum/options
  • asset format/size

Policy context

  • field classification
  • consent/legal exact text
  • expected purpose
  • risk/deadline context

Contract is embedded in the immutable bundle version. If the contract changes, autofill creates a new bundle version and supersedes old data requests.

Polling reconciler touches only user-data-dependent internal states: waiting_for_user_data, waiting_for_user_data_refresh, and user_data_pending.

6. Automation Bundle Lifecycle

A bundle is still the reusable automation unit. Data is requested only after the bundle is active/sufficiently validated.

7. Resolved Data Package

Autofill may store per job
  • resolved values/assets required for this application
  • provenance/confidence
  • permission/review flags
  • package id/version
  • validation result
Autofill must not store
  • full user profile
  • raw unstructured documents
  • unrelated user data
  • cross-application resolved-data cache

Asset access

User-data owns the asset library and returns metadata plus scoped access, usually signed temporary URLs/tokens. File bytes are not embedded in job payloads.

8. Policy and Approval Ownership

User-data decides data-level flags

  • allowed_to_use
  • requires_user_confirmation
  • sensitive category
  • consent status
  • confidence/source

Autofill decides final execution/submission

  • bundle risk
  • submission mode
  • deadline
  • approval state
  • legal/form gates

V1 caveat: submit-after-approval is best-effort; hard technical submit blocking remains future hardening.

10. Security, Privacy, and Audit

Sandbox

  • isolated container/VM
  • resource/time limits
  • no arbitrary runtime egress
  • browser traffic logged

Privacy

  • contract-scoped data only
  • raw user sources stay in user-data
  • artifact TTLs
  • erasure event handling

Audit

  • job/bundle events
  • data request/package ids
  • field provenance + use context
  • approval/submission evidence

Post-submission deletion is policy-dependent. Default: delete/anonymize user-specific snapshots/artifacts while keeping minimal anonymized audit if required.

11. V1 Risks / Future Hardening

Runtime language is not chosen yet.
Approval before submit is best-effort, not technically guaranteed.
User-data integration starts with polling; event-driven callbacks can be added later.
Smoke validation depends on safe submit-boundary detection.
Browser traffic is logged but not strictly allowlisted.
Platform-specific ToS automation checks are not modeled in v1.
